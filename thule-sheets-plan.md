# Thule Sheets — исследование и план разработки

Дата: 2026-10-22
Цель: веб-сервис табличного редактора уровня базового Google Sheets, в стиле macOS (тёмная тема по референсу), с интеграцией с таблицами PostgreSQL. Бэкенд — Python FastAPI.

---

## 1. Выводы

1. **Писать табличный движок самим не нужно.** Основа — **Univer Sheets (OSS, Apache-2.0)**, версия 1.0 вышла 2026-09-24. В открытой части уже есть: книги и листы, формулы (500+ функций), форматирование чисел, фильтр, сортировка, проверка данных (выпадающие списки), условное форматирование, комментарии, заметки, гиперссылки, поиск и замена, умные таблицы, закрепление, объединение ячеек, undo/redo, буфер обмена. Отрисовка на canvas — большие листы не тормозят.
2. **Чего нет в открытой версии Univer** (это Univer Pro, платно): совместное редактирование в реальном времени, история правок, импорт/экспорт XLSX, печать, диаграммы, сводные таблицы, вычисления на сервере, коннекторы данных.
   Решение для MVP — закрыть это своими силами на открытых библиотеках (ниже), а вопрос покупки Pro решить после PoC по цене и срокам.
3. **Таблицы PostgreSQL — отдельный режим просмотра**, а не «ещё один лист»: у них типизированные колонки, первичный ключ и потенциально миллионы строк. Для них — **Glide Data Grid (MIT, canvas, ленивая подгрузка)** с серверной пагинацией, а связь с книгами — через «связанные диапазоны» (результат запроса попадает в лист и обновляется).
4. **Бэкенд** — FastAPI + SQLAlchemy 2 (async) + asyncpg + Redis (pub/sub для WebSocket, присутствие пользователей) + фоновые задачи (Taskiq). Метаданные и содержимое книг хранятся в своей PostgreSQL.

## 4. Архитектура

```
Browser (React + TS + Vite)
 ├─ Shell в стиле macOS: сайдбар, хлебные крошки, тулбар, вкладки листов (shadcn/ui + Tailwind)
 ├─ Univer Sheets (canvas), собственный UI Univer скрыт, команды вызываются через Facade API
 ├─ Glide Data Grid — режим «таблица БД»
 ├─ ECharts — KPI-карточки и графики
 └─ WebSocket-клиент (операции, присутствие)
          │ REST (JSON) + WebSocket
FastAPI (Python 3.13, Pydantic v2, uvicorn)
 ├─ auth, workspaces, workbooks, sharing, versions
 ├─ collab-шлюз: упорядочивание операций, ревизии, рассылка
 ├─ import/export (openpyxl ⇄ снапшот Univer)
 ├─ pg-connector: подключения, интроспекция, строки, правки, запросы
 └─ фоновые задачи (Taskiq): импорт, экспорт, обновление связанных диапазонов, компактизация журнала
          │
 ├─ PostgreSQL (метаданные, снапшоты книг, журнал операций, аудит)
 ├─ Redis (pub/sub между воркерами, присутствие, rate limit, брокер задач)
 └─ S3-совместимое хранилище (MinIO) — файлы импорта и экспорта, вложения
```

### 4.1 Фронтенд

- **Своя оболочка, движок Univer внутри.** Референс — кастомный тулбар и меню, поэтому стандартные шапку и тулбар Univer скрываем, а кнопки вызывают команды через Facade API (`univerAPI.executeCommand`, `FRange.setFontWeight` и т. п.). Строка формул и выбор ячейки (`B9`) тоже свои, синхронизируются с выделением в Univer.
- **Тема.** Dark-first, акцент фиолетовый (≈ `#8B5CF6`), скругления 12–16 px, полупрозрачный сайдбар с `backdrop-filter: blur`, тонкие разделители `rgba(255,255,255,0.06)`. Цвета Univer (сетка, заголовки, выделение) задаются его темой; в PoC проверить, что canvas-часть корректно красится под тёмную тему.
- **Локализация.** Русская локаль UI Univer. Имена функций: в референсе `=СУММ(...)`. Хранить формулы с каноническими английскими именами, а русские показывать через слой локализации. В PoC проверить, поддерживает ли это Univer из коробки; если нет — отложить на этап после MVP.
- **Панель KPI** над листом (Доходы, Расходы, Остаток, Структура расходов) — отдельные виджеты на ECharts, привязанные к диапазонам или именованным ячейкам и пересчитываемые при изменении данных.

### 4.2 Бэкенд

- Python 3.13, FastAPI, Pydantic v2, SQLAlchemy 2.0 async + asyncpg, Alembic.
- Аутентификация: email + пароль (argon2 через `pwdlib`), JWT access + refresh в httpOnly-cookie; позже OAuth (Google) через Authlib.
- WebSocket в FastAPI + Redis pub/sub, чтобы несколько воркеров uvicorn видели одни и те же комнаты.
- Фоновые задачи: Taskiq с брокером на Redis.
- Наблюдаемость: structlog, OpenTelemetry, Sentry.
- Тесты: pytest + pytest-asyncio + httpx, testcontainers-postgres; фронт — Vitest + Playwright.

### 4.3 Хранение книг

- `workbook_snapshots` — полный снапшот книги (`IWorkbookData` Univer) в JSONB, сжатый на больших объёмах; новый снапшот каждые N операций.
- `workbook_ops` — журнал мутаций Univer с монотонной ревизией: `(workbook_id, rev, user_id, op jsonb, created_at)`.
- Загрузка книги = последний снапшот + операции после него.
- История версий = именованные снапшоты + журнал.
- Для очень больших листов позже — хранение ячеек блоками (например, 100 × 26), чтобы не перезаписывать весь JSON.

### 4.4 Совместное редактирование (своя реализация)

Univer построен на командах и мутациях, которые сериализуются в JSON. Протокол:

1. Клиент перехватывает локальные мутации (`onCommandExecuted`) и отправляет `{baseRev, ops[]}`.
2. Сервер — единственный арбитр порядка. Если `baseRev == headRev`, применяет операции, записывает в журнал, рассылает остальным с новой ревизией.
3. Если ревизия устарела: операции над разными ячейками коммутируют и принимаются; структурные операции (вставка и удаление строк и столбцов) при конфликте отклоняются, клиент подтягивает чужие операции и повторяет.
4. Присутствие: курсоры и выделения других пользователей, аватары в шапке — через Redis с TTL.

Риск: полноценный OT для структурных операций — самая сложная часть проекта. Если своя реализация не уложится в оценку, это главный аргумент за Univer Pro.

### 4.5 Модель данных (основное)

`users`, `workspaces` (Личные, Работа, Проекты…), `workspace_members`, `workbooks`, `workbook_snapshots`, `workbook_ops`, `workbook_shares (principal, role)`, `favorites`, `recent_views`, `db_connections`, `linked_ranges`, `audit_log`.

## 5. Интеграция с PostgreSQL

Нужно уточнить, какой из вариантов (или оба) нужен — см. раздел 8. План покрывает оба.

### 5.1 Подключения

- Пользователь добавляет подключение: host, port, db, user, password, SSL-режим, режим «только чтение» или «чтение и запись».
- Секреты шифруются (`cryptography`, Fernet или envelope-шифрование с ключом из KMS / переменной окружения), в API и логах не отдаются.
- Пул `asyncpg` на каждое подключение с лимитами, `statement_timeout`, `idle_in_transaction_session_timeout`.
- Для SaaS: защита от SSRF — запрет внутренних адресов (локальных сетей, метаданных облака), если это не self-hosted инсталляция.
- Позже: SSH-туннель.

### 5.2 Обзор и редактирование таблиц («живая таблица»)

- Интроспекция через `pg_catalog` / SQLAlchemy `inspect`: схемы, таблицы, представления, колонки, типы, PK, FK, индексы, оценка числа строк.
- Сайдбар: подключение → схема → таблица; открывается в Glide Data Grid.
- Чтение: keyset-пагинация по PK, серверные сортировка и фильтр. Фильтры — JSON-DSL, который компилируется в SQL через SQLAlchemy Core; идентификаторы всегда экранируются, значения передаются параметрами. Конкатенации строк SQL нет.
- Запись: только для таблиц с PK. Пакет правок в одной транзакции, оптимистическая блокировка (сравнение старого значения или `xmin`), приведение типов по типу колонки (numeric, date, timestamptz, bool, enum, json, array). Вставка и удаление строк.
- Редакторы ячеек по типу: дата — календарь, enum — выпадающий список, bool — чекбокс, FK — поиск по связанной таблице.
- Обновление: кнопка и автообновление по таймеру; собственные правки рассылаются по WebSocket. Позже, опционально: триггеры с `LISTEN/NOTIFY` (требуют прав на создание триггеров в БД пользователя).

### 5.3 SQL-редактор

- Редактор с подсветкой (CodeMirror 6, MIT) и автодополнением по схеме.
- `sqlglot` (MIT) — разбор запроса и определение, есть ли в нём запись; в режиме «только чтение» запрос выполняется в `SET TRANSACTION READ ONLY`.
- Лимит строк результата (например, 100 000), таймаут, отмена (`pg_cancel_backend`).

### 5.4 Связанные диапазоны (таблица БД ⇄ лист книги)

- Результат таблицы или запроса вставляется в лист как диапазон с отметкой источника; формулы и графики могут на него ссылаться.
- Обновление: вручную, по расписанию (Taskiq) или при открытии книги.
- Опционально — обратная запись: правки в связанном диапазоне с PK уходят в БД через тот же механизм, что и «живая таблица».
- Позже: собственная функция формул вида `=PG("conn", "select …")` (Univer поддерживает регистрацию пользовательских функций).

## 6. План работ

Оценка для команды из 2 разработчиков (1 фронтенд, 1 бэкенд/фулстек). Каждый этап заканчивается демонстрируемым результатом.

| # | Этап | Срок | Результат |
|---|---|---|---|
| 0 | **PoC и решение по движку** | 1–2 нед | Univer в React со своей тёмной темой и кастомным тулбаром; замер на 100k+ ячеек; перехват мутаций и их применение во втором окне; проверка русской локали и имён функций; черновой конвертер openpyxl ⇄ снапшот. **Решение: Univer OSS или Pro.** |
| 1 | Каркас | 2 нед | Монорепозиторий, docker-compose (Postgres, Redis, MinIO), CI (lint, типы, тесты), аутентификация, рабочие пространства, список файлов: Главная, Недавние, Избранное, Общий доступ |
| 2 | Редактор MVP | 3–4 нед | Создание и открытие книги, листы, тулбар и меню по макету, строка формул, автосохранение и индикатор «Сохранено», снапшоты |
| 3 | Совместная работа и доступ | 3–4 нед | WebSocket, журнал операций, присутствие и аватары, «Поделиться» с ролями, история версий |
| 4 | Импорт и экспорт | 1–2 нед | XLSX и CSV в обе стороны, стили и формулы в базовом объёме |
| 5 | PostgreSQL | 4–5 нед | Подключения, обзор схем, живая таблица с редактированием, SQL-редактор, связанные диапазоны |
| 6 | Дашборд и графики | 2 нед | KPI-карточки и графики над листом, привязанные к диапазонам |
| 7 | Доводка и запуск | 2 нед | E2E-тесты, нагрузочный тест WebSocket, аудит безопасности (OWASP), мониторинг, деплой |

**Итого: ~18–23 недели** на MVP. С Univer Pro этапы 3, 4 и 6 сокращаются примерно на 4–6 недель, но добавляется стоимость лицензии и интеграция с их сервером коллаборации (не на Python).

### Порядок внутри этапов

- Сначала вертикальный срез (одна книга, один пользователь, сохранение), затем ширина.
- Этап 5 можно вести параллельно с этапами 3–4: он почти не пересекается с редактором.

## 7. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Своя коллаборация над мутациями Univer сложнее оценки (структурные операции) | Высокая | PoC на этапе 0; запасной путь — Univer Pro; на MVP допустимо отклонять конфликтующие структурные операции |
| Конвертация XLSX теряет форматирование | Средняя | Поддерживаемое подмножество фиксируется явно; тесты на наборе реальных файлов |
| Тёмная тема не полностью применяется к canvas Univer | Средняя | Проверка в PoC |
| Локализованные имена функций (`СУММ`) | Средняя | Канонические английские имена в хранилище, перевод на уровне UI |
| Безопасность внешних подключений к БД (SQL-инъекции, SSRF, утечка паролей) | Средняя | Только параметризованные запросы, экранирование идентификаторов, шифрование секретов, read-only по умолчанию, аудит |
| Большие таблицы БД | Средняя | Keyset-пагинация, лимиты, ленивая загрузка в Glide |
| Зависимость от одного вендора (Univer) | Низкая–средняя | Apache-2.0: при необходимости форк; бизнес-логика отделена от движка через свой слой команд |

## 8. Открытые вопросы

1. **PostgreSQL:** подключение внешних баз пользователей, работа с таблицами внутри собственной БД сервиса или оба варианта?
2. **Модель продукта:** публичный SaaS с регистрацией или внутренний инструмент (self-hosted)? От этого зависят SSRF-ограничения, биллинг и SSO.
3. **Бюджет на Univer Pro:** допустим ли? Сильнее всего влияет на сроки.
4. **Совместная работа в MVP:** нужна сразу в реальном времени или достаточно «один редактирует, остальные видят обновления»?
5. **Мобильная версия:** нужна ли в MVP?
6. **Офлайн и десктоп-обёртка** (Tauri/Electron) для настоящего macOS-приложения или только веб в стиле macOS?
